### Two genuine "new chrome breaks an old locator" bugs found — not
### regressions, both fixed by scoping the *test*, never the app (D98/D99)

1. **The persistent Sidebar (D93) repeats every visible entry-point label
   on every page**, including Dashboard Home's own "Choose a task" card
   grid of the same entries. `dashboard.spec.ts`'s unscoped
   `getByText(label, {exact:true})`/`getByRole("listitem")` started
   matching both the sidebar link and the dashboard card — a strict-mode
   violation. Fixed by scoping to `page.locator("main")` (AppShell's
   `<main>` wraps only the routed page content, the Sidebar is `<main>`'s
   sibling, not inside it). Same fix applied to one more file:
   `agreement-history.spec.ts`'s "Existing Company links to Agreement
   History" test — the Sidebar's own "Agreement History" nav link now
   collides with `ExistingCompanyPage`'s inline link of the same name.
   **General lesson for any future page whose test locates an entry-point
   label without a role/scope constraint**: grep all spec files for the
   ten entry labels before restyling a new page, since the Sidebar now
   makes every one of them ambiguous app-wide.
2. **The shared Topbar (D87) puts one real `<input type="text">` search
   box on every authenticated page.** `existing-company.spec.ts`'s AC7
   ("nothing on the read-only Payroll Details page is editable") asserted
   `getByRole("textbox")` count 0 — now genuinely false, since chrome
   exists where none did before. Fixed by asserting exactly one textbox,
   named "Search", instead of zero — the assertion's *intent* (no editable
   payroll data) is unchanged.
